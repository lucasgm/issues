Write-time telemetry vs. live catalog commit diffing

A detailed comparison of the original catalog-first hybrid and the proposed checkpoint-emission design, including corrections, implementation difficulty, file impact, and the recommended production architecture.

Verdict

The write-time checkpoint proposal is the better live architecture for business telemetry. It has better request correlation, lower semantic ambiguity, lower latency, and avoids complex interpretation of catalog merge history. The original live catalog-diff exporter should be rejected as the primary real-time mechanism.

However, the proposed design is not complete as written. The production recommendation is an enhanced write-time hybrid:

  1. Emit domain events at existing authoritative workflow checkpoints.
  2. Use one shared composite action only to validate and deliver event batches to Splunk HEC.
  3. Add centralized GitHub workflow telemetry for failures and cancellations that never reach those checkpoints.
  4. Use a periodic catalog snapshot reconciliation as a safety net.
  5. Use catalog history extraction only for a controlled one-time backfill.

This is an evolution of the hybrid recommendation: the catalog remains the authoritative final-state evidence, but live event creation happens where full context already exists.

Why write-time emission is better here

1. The workflow already derives the business payload

The image request workflow’s catalog-verification loop already resolves each requested image, normalized tag, catalog status, Artifactory path, and security-report link, then classifies the item as published, scan-gated, EOL, or not cataloged. That is exactly the information needed for an artifact outcome event.

The Windows request workflow has a similar post-run catalog lookup and checks both workflow conclusion and catalog state before it closes the issue. Helm downloads per-chart status artifacts and derives an individual result and reason. These are stronger semantic checkpoints than reconstructing intent from a later catalog commit.

2. Correlation exists before catalog persistence

IssueOps knows the issue number, request item, vendor, requested reference, dispatch run ID, and requester context. Those values do not reliably exist in catalog Git history. Capturing them at request time avoids an Actions API history lookup and avoids maintaining a run-ID-to-issue database.

3. Catalog history contains transport and tooling behavior

Catalog Git history records how automation merges and maintains files, not only business transitions. Merge commits and periodic metric-report commits are legitimate repository activity but introduce noise for a live event interpreter.

4. It matches the acceptance criteria

Request initiation, early validation failure, scan initiation, scan failure, and time-to-approval cannot be derived from a final catalog change. Write-time producers can emit those events at their authoritative boundaries.

Why catalog JSON files are not a good primary telemetry source

The catalog is valuable and should remain part of the design, but it solves a different problem. Catalog JSON represents the latest known artifact state. Telemetry represents events that occurred over time. Treating the files themselves as the event stream creates several correctness problems.

1. Current state is not event history

When a catalog entry changes from inactive to active, the JSON normally retains the new state. It does not inherently preserve a first-class event saying who changed it, why it changed, which request caused it, how long approval took, or what the previous state meant. Git can sometimes reconstruct the difference, but that is repository history reconstruction—not an explicit business event contract.

2. Reposting complete files creates duplicate observations

If a complete provider JSON file is sent whenever one artifact changes, every unchanged artifact in that file is sent again. Splunk then sees repeated observations that can be mistaken for new whitelists, scans, or approvals. Dashboards must perform expensive latest-record deduplication, and a small error in that logic inflates cumulative and time-series counts.

3. Catalog persistence excludes unsuccessful attempts

Invalid requests, source authentication failures, pull errors, scanner outages, cancelled workflows, and other pre-catalog failures may produce no catalog record at all. A catalog-only feed therefore has an incomplete denominator for approval rate, ingestion failure rate, and pipeline success rate.

4. Request correlation is incomplete

The catalog generally knows the artifact and the workflow run that wrote it, but not necessarily the originating issue or request item. A single issue can request multiple artifacts, and scheduled discovery may have no issue. Reconstructing issue correlation later requires API lookups and state that the catalog does not own.

5. The JSON shapes are intentionally different

Containers and libraries are nested differently, packages have flat release structures, and Helm includes chart and nested-image information. Fields such as digest, sunset date, malware result, suppression details, and Artifactory path are not uniformly available. Sending raw files pushes this schema complexity into every Splunk search.

6. Git history contains implementation noise

Merge commits, branch consolidation, generated metrics commits, formatting-only changes, and derived-file updates are repository operations rather than business outcomes. A live diff engine must distinguish semantic artifact transitions from those implementation details.

7. Deletion and absence are ambiguous

An artifact missing from a new file might represent an intentional removal, blackout, schema migration, merge conflict, generated-file replacement, or processing error. A write-time artifact_removed or artifact_blacked_out event can state the reason explicitly.

8. Full catalog payloads are larger than normalized events

Provider files may repeat large vulnerability summaries and metadata for many releases. Normalized change events send only the affected artifact and fields, reducing HEC volume and improving field consistency.

Impact of Splunk’s 40-day data-retention limit

A 40-day retention period materially changes the reporting design. Splunk can provide excellent operational and security visibility for the recent window, but it cannot be the only durable system for cumulative, long-term, or compliance history.

If the organization cannot provide any Splunk index with retention longer than 40 days, the dashboards must clearly separate:

  • Current state — rebuilt from the latest catalog snapshot.
  • Rolling metrics — explicitly labeled “last 40 days.”
  • Long-term aggregates — read from an approved durable store or regenerated from authoritative history.
Acceptance-criteria conflict: Dashboard 4’s historical whitelist changes and lifecycle timeline cannot be fully satisfied by a 40-day-only Splunk index. Either the requirement must be defined as a rolling 40-day view, or a longer-retention summary/archive must be approved.

Backfill implication

A large historical backfill into a 40-day-retention raw index has limited value because it will expire according to index policy. Before running the backfill, decide whether it is intended only to initialize current dashboards, populate a longer-retention summary index, or create an external compliance archive. Do not spend effort importing years of detailed events into an index that will discard them shortly afterward.

Snapshot cadence

The reconciliation snapshot must run comfortably within the retention window. Daily is recommended for current-state recovery and operational confidence. Every snapshot should carry a snapshot_id, snapshot_at, and artifact count. Splunk searches should select the latest complete snapshot rather than unioning multiple snapshots as new whitelist events.

Recommended treatment for scheduled runs

Scheduled image discovery and scanning must be instrumented separately from IssueOps. Although there is no user request or issue, it is still a GitHub Actions run with github.event_name == 'schedule'. The important difference is that it produces system-initiated artifact events rather than request events.

Events to emit

For scheduled runs, do not emit whitelist_request_initiated. Instead emit:

release_detected
scheduled_ingestion_started
vulnerability_scan_started
vulnerability_scan_completed
catalog_publish
catalog_scan_gated
scheduled_ingestion_failed

These events have no request_issue, which is correct.

{
  "event_type": "release_detected",
  "trigger_type": "schedule",
  "initiator_type": "system",
  "request_issue": null,
  "artifact_id": "dockerhub:library/nginx:1.28.0",
  "source_workflow": "dockerhub-workflow-image-lifecycle.yml",
  "source_run_id": "18452001",
  "detected_at": "2026-07-20T10:03:12Z"
}

The scheduled image lifecycle has several meaningful checkpoints:

The event producer is the scheduled lifecycle workflow itself. The shared composite action only delivers the generated batch to Splunk.

Avoid one HEC call per matrix step

Scheduled lifecycle workflows can process many images through matrices. Calling Splunk for every command would be inefficient. Use this pattern:

  1. The discovery job writes release-detected.ndjson.
  2. Call emit-telemetry once to send the discovery batch.
  3. Each scan matrix job writes its artifact-level result file.
  4. Upload those files as GitHub run artifacts.
  5. The consolidation job downloads and combines them.
  6. After the catalog update, call emit-telemetry once with the final batch.
- name: Build scheduled discovery events
  run: |
    # Existing discovery output is transformed into:
    # telemetry/release-detected.ndjson

- name: Emit release-detected events
  uses: ./.github/actions/emit-telemetry
  with:
    event-file: telemetry/release-detected.ndjson

The final consolidation job can send vulnerability_scan_completed, catalog_publish, catalog_scan_gated, and scheduled_ingestion_failed.

Operational versus artifact events

The centralized GitHub collector still sends the run-level event:

{
  "event_type": "workflow_completed",
  "trigger_type": "schedule",
  "workflow_conclusion": "success",
  "source_run_id": "18452001"
}

That answers: “Did the scheduled automation run successfully?”

The lifecycle workflow sends artifact-level events:

{
  "event_type": "catalog_scan_gated",
  "artifact_id": "dockerhub:library/nginx:1.28.0",
  "policy_gate": "fail",
  "reason_category": "critical_vulnerability",
  "source_run_id": "18452001"
}

That answers: “What happened to this specific discovered image?” Both events are required.

Correlation without an issue number

Scheduled artifacts should be joined using artifact_id, source_run_id, source_workflow, processing_id, and catalog_commit when available.

{
  "processing_id": "18452001:dockerhub:library/nginx:1.28.0",
  "artifact_id": "dockerhub:library/nginx:1.28.0",
  "request_issue": null
}

request_issue: null is not a data gap. There was no request.

Keep scheduled and request-driven metrics separate

Do not mix scheduled discovery latency with human request approval time.

Issue-driven:
time_to_approval = policy_decision_at - request_initiated_at

Scheduled discovery:
time_to_ingest = cataloged_at - detected_at

Include the following dimensions in Splunk:

trigger_type = issue | schedule | workflow_dispatch | recurring_scan
initiator_type = user | system

This lets dashboards separate request-driven approvals, automatically discovered releases, scheduled ingestion success rate, scheduled scan failure rate, detection-to-publication time, and user request-to-approval time without mixing their denominators.

Failure and reconciliation behavior

If Splunk is unavailable, the scheduled workflow must continue, the failed batch must be visible and replayable, the daily catalog snapshot should restore the latest final state, and the central workflow collector should still report the failed or successful run when possible.

The snapshot cannot recreate precise events such as vulnerability_scan_started, but it can recover the final catalog state.

    └── request and artifact outcome events

Scheduled lifecycle workflow
    └── discovery, ingestion, scan and artifact outcome events

    └── operational run events for both trigger types

    └── final-state recovery and consistency validation
Scheduled image processing uses the same hybrid architecture with trigger_type: schedule, no request issue, and business events emitted from the lifecycle workflow rather than image-request-ops.yml.

Corrections required before adopting the new proposal

Correction 1 — a composite action cannot be invoked inside a shell loop. The existing verification is one large run: step. It should append normalized events to an NDJSON batch file and expose its path; the next workflow step invokes emit-telemetry once to send the batch.
catalog verification shell loop
  └── append one JSON event per artifact to telemetry-events.ndjson

following workflow step
  └── uses: ./.github/actions/emit-telemetry
      with:
        event-file: telemetry-events.ndjson
Correction 2 — request workflows do not observe every catalog mutation. Vendor lifecycles also run on schedules and can discover new releases without an issue. npm, PyPI, Helm, Windows, recurring scans, blackouts, and package merge paths mutate catalog state independently. The request-workflow checkpoints cover request-driven outcomes, not the complete publication universe.

For full “new releases detected” and catalog lifecycle reporting, either instrument the category-specific catalog-write checkpoints or accept that the reconciliation snapshot will report these later without request context. The latter is acceptable for an initial phase but not for real-time completeness.

Correction 3 — direct fail-soft delivery is not durable. Always exiting zero protects publication, but || true alone silently loses events. The action must return a delivery status, add a warning/job summary, and retain the failed batch as an artifact or otherwise make it replayable. Reconciliation protects final catalog state but cannot reconstruct every request or scan-start event.
Correction 4 — “full snapshot diff” needs durable state. A job cannot emit only changed hashes unless it has a reliable previous-hash store. The simplest safety net is to send a complete periodic snapshot to a separate sourcetype with a snapshot_id. If changed-only reconciliation is required, define a durable checkpoint store explicitly.
Correction 5 — one artifact ID is insufficient for generic or unresolved requests. At request initiation, a generic tag may not yet resolve to the final catalog version or digest. Use a durable request_item_id for the requested item and a separate resolved artifact_id when the concrete version is known.
Correction 6 — operational telemetry is still required. The proposed schema omits workflow-start/completion/cancellation events and detailed scan lifecycle events needed by the Operational Metrics dashboard. A central collector remains part of the final hybrid architecture.

Live mechanism

Use write-time emission for events where a workflow already knows the authoritative transition. Do not run a live catalog Git-history walker.

Safety net

Send a daily complete catalog snapshot, or a changed-only snapshot backed by a clearly defined durable hash store. Compare the snapshot with latest live artifact state in Splunk and alert on missing or inconsistent events. The snapshot ensures current inventory remains recoverable within the 40-day retention window.

Historical bootstrap

Use extract_from_catalog_commits.py once only when the destination has suitable retention or when generating long-lived aggregates. Tag all such events source_type=backfill and document that request correlation is unavailable. Leave metrics-catalog.yml unchanged for its existing local reports.

Long-term reporting

Retain catalog Git history and request records as the durable evidence layer. If Splunk offers a longer-retention summary or metrics index, populate it with daily/weekly aggregates. Otherwise, store those aggregates in an approved durable reporting system and label raw Splunk dashboards as rolling 40-day views.

Recommended identity and event schema

Retain the draft’s intersection fields and extra bag, but use two correlation identities:

  • request_item_id: created per artifact in an issue, such as a hash of repository, issue number, item index, and normalized requested reference. It exists before a concrete release is known.
  • artifact_id: identity of the resolved catalog artifact/version; include digest when it is stable and available, but do not require it for artifact kinds that lack one.

Final decision

Choose the write-time checkpoint approach over the live catalog commit-diff exporter. It is a better fit for this repository because the workflows already possess the issue, artifact, status, scan, and publication context that the catalog history cannot reliably reconstruct.

Do not adopt the draft unchanged. Add a central workflow collector, use a dual request-item/artifact identity, batch events before invoking the composite action, make failed deliveries observable and replayable, and define a durable reconciliation model. Expand instrumentation deliberately because the request workflows alone do not cover every scheduled catalog writer.

Because Splunk retains data for only 40 days, use it for recent events and operational analysis—not as the sole compliance archive. Rebuild current inventory from daily catalog snapshots, preserve catalog/request history as durable evidence, and obtain a longer-retention summary/metrics index or approved external aggregate store for monthly, cumulative, and compliance reporting.

Use the composite action as shared transport; use existing workflow checkpoints as domain-event producers; use catalog snapshots as reconciliation and current-state recovery; use catalog history as durable evidence and selective backfill—not as the live event feed.
