I would only use a composite action as the low-level, shared Splunk HEC sender—not as something manually added to every scan and publication job.

Existing catalog metrics implementation

There is already a strong foundation:

  • metrics-catalog.yml (line 1) clones the catalog with full history.
  • extract_from_catalog_commits.py (line 42) walks commits touching catalog JSON files.
  • It produces normalized software_added, release_added, and scan_updated records.
  • Events include vendor, software, tag, scan counts, policy gate, Artifactory path, commit, and sometimes workflow run ID; see extract_from_catalog_commits.py (line 113).

This is the best starting point for Splunk business reports, but it is not ready unchanged.

Gaps that should be fixed

The workflow is not event-driven by catalog changes.

Its push trigger applies to this automation repository, not the separately checked-out catalog repository. Catalog updates therefore reach metrics through the daily schedule, unless this source repository also happens to receive a push. See metrics-catalog.yml (line 3).

It rebuilds all history every day.

Each run checks out the full history and reconstructs every version of every catalog file. That will become progressively slower and creates repeated Splunk delivery unless forwarding implements checkpoints and deterministic IDs.

The extractor omits library catalogs.

It scans only:

  • vendor-catalog/containers
  • vendor-catalog/charts
  • vendor-catalog/packages

See extract_from_catalog_commits.py (line 380). The architecture says npm and PyPI write under vendor-catalog/library, so those results would not reach Splunk.

It does not emit removals or blackout events.

The comparisons find additions and security changes, but do not detect removed releases, status-only changes in all schemas, blackout reasons, restored artifacts, suppression changes, or suppression expiry.

Package scan detection is incomplete.

Container events compare both scanned_date and policy_gate, while packages compare only policy_gate. Two package scans with the same outcome are therefore invisible.

run_id correlation is best-effort.

It is parsed from the commit subject using run <digits>. See extract_from_catalog_commits.py (line 82). Some workflows follow this convention, but it is not enforced across every catalog writer.

Event time is ambiguous.

timestamp is the catalog commit time, while scanned_date is separate. Splunk should preserve both as observed_at and occurred_at; otherwise dashboards can report activity in the wrong interval.

The current metrics workflow modifies the catalog.

It generates reports and commits them back to the catalog at metrics-catalog.yml (line 59). Splunk forwarding should not require writing generated metrics into the source-of-truth repository.

Recommended design

1. Catalog outcome exporter

Run this from RECORE.third-party-catalog, triggered by catalog changes on main, with path filters for the authoritative JSON directories.

It should:

  • Compare the pushed commit range, rather than replay all history.
  • Normalize artifact events across images, Helm, libraries, and packages.
  • POST batches to Splunk HEC.
  • Use deterministic event IDs for idempotency.
  • Retry transient failures with backoff.
  • Save a delivery artifact/log, but never expose the HEC token.
  • Optionally run a scheduled reconciliation to recover missed pushes.

Suggested event types:

  • artifact_requested
  • artifact_discovered
  • scan_completed
  • artifact_published
  • artifact_scan_gated
  • artifact_suppressed
  • artifact_blacked_out
  • artifact_removed
  • artifact_restored
  • catalog_write_completed

For final-state reporting, artifact_published should require catalog status active or suppressed and a valid Artifactory destination—not merely a successful workflow.

2. Central GitHub Actions collector

Add one centralized workflow using workflow_run: completed for the production workflow names. It should send one operational record per completed run to Splunk:

  • repository and workflow
  • run ID and attempt
  • event type
  • actor
  • branch and SHA
  • created, started, and completed timestamps
  • conclusion
  • run URL
  • triggering issue/request number when available

If job-level failure reporting is required, it can query the Actions API for job names, durations, and failed steps.

This captures failures and cancellations that never produce a catalog commit. It avoids editing every lifecycle workflow.

If GHES supports reliable organization/repository webhooks to an internal collector, a GitHub App/webhook receiver is even stronger than workflow_run, particularly for queued and in-progress events. The receiver can relay to Splunk independently of runner availability.

3. Correlation contract

Make these fields mandatory across both streams:

{
  "schema_version": "1.0",
  "event_id": "sha256-of-source-and-natural-key",
  "source": "github_actions|third_party_catalog",
  "repository": "icesdlc/RECORE.third-party",
  "workflow_name": "DockerHub Image Lifecycle",
  "run_id": "123456",
  "run_attempt": 1,
  "request_issue": 1234,
  "artifact_type": "image",
  "vendor": "dockerhub",
  "artifact": "library/nginx",
  "version": "1.27.0",
  "scan_gate": "pass",
  "catalog_status": "active",
  "publication_status": "published",
  "occurred_at": "...",
  "observed_at": "..."
}

The most important implementation change is to stop deriving run_id from free-form commit messages. Write structured provenance into catalog entries or into a small commit-side event manifest:

  • workflow_repository
  • workflow_name
  • workflow_run_id
  • workflow_run_attempt
  • request_issue
  • source_config_commit

Final recommendation

Use the catalog-forwarding approach as the primary source for business and compliance reports because it represents the real artifact outcome. Add a centralized workflow_run or GitHub webhook collector for Actions reliability and performance reports.

Do not instrument every lifecycle workflow with a Splunk composite action. If a composite action is created, limit it to a reusable, hardened HEC delivery implementation used by the two centralized exporters.

A sensible rollout would be:

  1. Define the event schema and Splunk index/sourcetypes.
  2. Extend the extractor to support incremental commit ranges, libraries, removals, suppression, blackout, and deterministic IDs.
  3. Move catalog export triggering to the catalog repository.
  4. Add the centralized Actions completion collector.
  5. Backfill historical catalog events once.
  6. Enable scheduled reconciliation and delivery monitoring.

This gives accurate reports without coupling Splunk availability to the critical scan-and-publish path. No repository files were changed during this review.
