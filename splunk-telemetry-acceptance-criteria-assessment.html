Verdict

No—the last proposal provides the right overall architecture, but as currently written it would not satisfy all acceptance criteria. It covers most final catalog and workflow-completion outcomes, but additional event sources, timestamps, and event types are required.

The hybrid approach should remain, because neither catalog history nor GitHub Actions telemetry can meet the requirements independently.

Most important gaps

1

Request events need a third event source

The proposed design has two sources: GitHub workflow telemetry and catalog changes. The acceptance criteria require a third logical source: request/IssueOps events.

The catalog cannot report rejected requests that never produce an entry. A workflow-completion event can say a workflow failed, but it cannot reliably say whether the business request was rejected, validation failed, the image was past EOL, or infrastructure failed.

Add a request-event producer to image-request-ops.yml for:

  • whitelist_request_initiated
  • whitelist_request_validated
  • whitelist_request_rejected
  • approval_workflow_triggered

This can use the common Splunk sender action without spreading telemetry throughout every vendor lifecycle.

2

workflow_run: completed is insufficient for start events

The centralized completion collector covers pipeline results, but not ingestion attempt time, approval workflow trigger time, scan initiation time, or precise stage duration.

Use GitHub webhooks for requested, in-progress, and completed workflow activity, or combine a centralized completion collector with explicit start events at the few meaningful business stages.

Practical solution: use a GitHub webhook/collector for workflow start and completion, a RequestOps event for request initiation, a scanner wrapper/composite for scan start and completion, and the catalog exporter for authoritative final outcomes.
3

Scan failures may never appear in the catalog

Catalog extraction works when a scan result is written as inactive, but not necessarily when scanner setup fails, Aqua is unavailable, the image cannot be pulled, validation fails before scanning, the runner terminates, or catalog consolidation fails.

Required scan events:

vulnerability_scan_initiated
vulnerability_scan_completed
vulnerability_scan_failed

The completed event should include critical, high, medium, and low counts; total vulnerabilities; policy gate; report URL; scanner result; artifact identity and digest; scan duration; and suppression status.

4

Approval and publication must be distinguished

The acceptance criteria use “approved,” “whitelisted,” and “ingested.” These should not be treated as synonyms.

For example, a security scan may be approved but the Artifactory push may fail. Reporting that image as whitelisted would be incorrect.

An image is whitelisted only when its catalog status is active or suppressed, it has an Artifactory destination, and catalog publication has completed.
5

Expiration and renewal require a data-model decision

The existing catalog has concepts such as sunset_date and suppression expiry, but those do not necessarily mean whitelist expiration.

The team must define whether every whitelist has an expiry date, whether vendor EOL is the whitelist expiration, whether suppression expiration is separate, and what constitutes renewal.

{
  "whitelist_status": "active",
  "whitelist_effective_at": "2026-07-19T12:00:00Z",
  "whitelist_expires_at": "2027-07-19T12:00:00Z",
  "renewal_number": 1,
  "renewal_reason": "annual-review"
}

Then emit whitelist_expiration_scheduled, whitelist_expired, whitelist_renewal_requested, and whitelist_renewed. Without an authoritative expiration field, the compliance dashboard cannot be accurate.

Time-to-approval calculation

Capture at least the following timestamps:

request_initiated_at
approval_workflow_triggered_at
policy_decision_at
published_at
cataloged_at

Define the primary approval metric explicitly:

time_to_approval = policy_decision_at - request_initiated_at

A separate metric should measure end-to-end delivery:

time_to_whitelist = cataloged_at - request_initiated_at

Splunk can calculate average, P50, P95, and P99 only when events share a durable correlation key such as request_id + artifact identity + requested version. A GitHub run ID alone is inadequate because request processing and vendor lifecycle execution can use different runs.

Dashboard readiness

The architecture can support all four dashboards after these additions, but the dashboards themselves still need Splunk SPL definitions and visual configuration.

DashboardRequired data foundation
Image Whitelisting OverviewCatalog outcomes plus request approval/rejection events and normalized vendor/registry.
Security & Vulnerability MetricsScan-start, completion, failure and severity events plus actionable catalog status.
Operational MetricsWorkflow lifecycle events, correlated request timestamps, failure taxonomy and release detection.
Compliance & AuditAppend-only lifecycle events, expiration/renewal data, historical decisions and policy violations.
Compliance requirement: current-state catalog JSON alone is insufficient because later updates overwrite prior state. Catalog Git history can reconstruct changes, but exporting append-only lifecycle events to Splunk is more dependable for audit reporting.

Revised recommendation

Keep the hybrid proposal, expanded to four collection points:

IssueOps/request events
→
Request initiated, validation, and early rejection
GitHub workflow events
→
Workflow triggered, started, completed, and cancelled
Scan/pipeline events
→
Ingestion attempt, validation, scan initiated, completed, or failed
Catalog change events
→
Approved final state, published, expired, renewed, removed, or restored
Splunk HEC → Operational + Security + Audit dashboards

The common composite action is appropriate as the secure Splunk transport used at these controlled collection points. It should implement batching, retries, schema validation, secret handling, and non-blocking delivery. It should not be copied after every job.
