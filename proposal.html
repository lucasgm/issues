Catalog-first, then hybrid: the recommended Splunk approach

A reassessment that excludes generated NDJSON and local reports from Splunk and uses authoritative catalog changes as the first dependable business-data source.

Reassessed decision

Yes, the authoritative catalog JSON files are the correct place to start. The recommendation remains hybrid, but its implementation order should be catalog-first rather than attempting all telemetry sources simultaneously.

The generated files under metrics/ should not be sent to Splunk. They are derived reporting products, not authoritative records. The first Splunk integration should read changes from explicitly approved catalog JSON paths, create normalized change events, and establish reliable business metrics. Request, scan-start, and GitHub operational telemetry should then be added to fill the requirements the catalog cannot observe.

Important refinement: do not ingest “all other JSON files” indiscriminately. Ingest only an allowlist of authoritative catalog datasets. Catalog repositories often also contain generated indexes, configuration, schemas, cached data, and presentation files that would duplicate or distort the same artifacts.

Explicit source boundary

Excluded from Splunk

  • metrics/events/additions.ndjson
  • metrics/events/scans.ndjson
  • metrics/events/all-events.ndjson
  • metrics/REPORT.md
  • metrics/DASHBOARD.html

These files are regenerated from history for local reporting. Consuming them would add another processing dependency, replay historical records, and create duplicate-delivery and checkpoint problems.

Candidate authoritative inputs

  • vendor-catalog/containers/*.json
  • vendor-catalog/charts/*.json
  • vendor-catalog/library/*.json
  • vendor-catalog/packages/*.json

The automation repository confirms these logical catalog areas: container providers, Helm charts, npm/PyPI libraries, and vendor packages. The exact file inventory and schemas must be validated in RECORE.third-party-catalog before implementation because that repository is not present in the current workspace.

Selection rule

A JSON file should be admitted only when it is an authoritative record of an artifact’s current state. Derived rollups, generated site data, indexes, cached API responses, and metrics output should be excluded even if they are JSON.

Why catalog-first is the right starting point

Authoritative final state

The request workflow already verifies the catalog rather than treating a green lifecycle run as proof of publication.

Rich business metadata

Catalog entries carry status, scan dates, policy gate, vulnerability summaries, Artifactory location, sunset data, and suppression details.

Cross-workflow normalization

Vendor-specific workflows differ greatly, but their results converge into a much smaller number of catalog schemas.

Lower initial change risk

A catalog exporter avoids inserting Splunk network calls into the critical retrieve, scan, sign, and publish paths.

Historical bootstrap

The current catalog provides an initial inventory; Git history can support a controlled one-time backfill if historical trends are required.

Operational isolation

Splunk availability does not determine whether an image can be scanned or published.

This phase can immediately support the strongest catalog-backed metrics: current whitelist inventory, new cataloged images and releases, vendor distribution, final security posture, remediation lists, and catalog lifecycle changes.

What catalog JSON cannot prove

Catalog-first is a starting phase, not the complete acceptance-criteria solution. An artifact that never reaches the catalog leaves no authoritative catalog record.

Do not forward full files on every change

The catalog is a current-state database stored in Git. Splunk is an event and analytics platform. The integration must translate state changes into append-only events rather than repeatedly posting complete files.

→
Schema-aware diffCompare the before and after commit for each artifact identity
→
Normalized Splunk eventsOnly additions, transitions, scans, removals, suppression and lifecycle changes

Two complementary datasets

  • Current-state snapshot: one controlled initial load, and optionally a periodic reconciliation, containing the latest state of every artifact.
  • Change-event stream: an event-driven diff for every subsequent authoritative catalog commit.

The snapshot answers “what is whitelisted now?” The change stream answers “what changed, when, and from which previous state?” Keeping these concepts separate prevents historical dashboards from counting the same unchanged artifact every day.

Deterministic identity

Define artifact identity by type and schema—for an image, normally normalized source registry, repository, tag/version, and digest where available. Build event_id from source repository, catalog commit, event type, and artifact identity. Splunk retries then become idempotent.

Structured provenance

Where possible, add workflow repository, workflow run ID, run attempt, request issue, and source-config commit to catalog entries or a companion event manifest. Do not depend on parsing free-form Git commit subjects.

Splunk data design

Use separate sourcetypes so operational events do not become confused with business state:

  • recore:thirdparty:catalog_state — controlled current-state snapshots
  • recore:thirdparty:catalog_change — append-only artifact transitions
  • recore:thirdparty:request — request initiation, validation and decision
  • recore:thirdparty:scan — scan lifecycle and severity results
  • recore:thirdparty:workflow — GitHub operational health

These may share one index initially if retention and access controls are the same, but sourcetypes and field names should remain distinct.

Dashboard calculation rules

  • Current total: latest catalog state per artifact identity, filtered to active or non-expired suppressed entries with a valid Artifactory path.
  • Whitelist trend: first transition into a published whitelist state during the period.
  • Approval rate: approved request decisions divided by all terminal request decisions—not successful workflows divided by workflow runs.
  • Ingestion failure rate: failed terminal ingestion attempts divided by all terminal ingestion attempts.
  • Vulnerable at ingestion: severity counts from the first completed scan associated with the ingestion attempt, excluding routine rescans.
  • Remediation list: latest state per artifact where policy gate fails, status is inactive, or suppression is near expiry.

Phased implementation plan

Phase 0

Inventory the catalog repository. Classify every JSON path as authoritative, derived, configuration, or presentation. Approve schemas, natural keys, status meanings, and the whitelist definition.

Phase 1

Load one current-state snapshot from authoritative catalog files. Validate totals against ICEDevX/catalog expectations. Do not derive historical trends from repeated snapshots.

Phase 2

Deploy the catalog commit-range exporter on main with path filters, deterministic IDs, schema validation, HEC batching, retry, redaction, and non-blocking failure behavior.

Phase 3

Perform one controlled historical backfill from catalog Git history into the catalog-change sourcetype. Record a backfill version and cutoff so live events do not overlap.

Phase 4

Add request events from IssueOps for initiation, validation, approval/rejection and renewal. This establishes correct approval-rate denominators and request timestamps.

Phase 5

Add scan start/completion/failure events and centralized GitHub workflow telemetry. This completes ingestion failures, reason categories, duration percentiles, and pipeline health.

Phase 6

Implement the four dashboards, reconciliation monitoring, dead-letter/replay procedure, schema-version alerts, and compliance retention controls.

Final recommendation

Proceed with a catalog-first hybrid architecture. Begin with an allowlisted set of authoritative catalog JSON files, not the generated metrics products and not every JSON file in the repository. Establish a current-state snapshot and an incremental catalog-change stream as the foundation for business, vulnerability, vendor, remediation, and audit metrics.

Then add IssueOps request events, scan lifecycle events, and centralized GitHub operational events. These additions are not architectural replacements; they complete the acceptance criteria that catalog data cannot observe, especially rejected requests, pre-catalog failures, scan initiation, pipeline health, and time-to-approval percentiles.

The recommendation has not changed from hybrid to catalog-only. It has become more precise: catalog data is the first and authoritative business-outcome layer; the hybrid sources are added deliberately to complete the event lifecycle.
