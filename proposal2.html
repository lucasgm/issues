Write-time telemetry vs. live catalog commit diffing

A detailed comparison of the original catalog-first hybrid and the proposed checkpoint-emission design, including corrections, implementation difficulty, file impact, and the recommended production architecture.

Verdict

The write-time checkpoint proposal is the better live architecture for business telemetry. It has better request correlation, lower semantic ambiguity, lower latency, and avoids complex interpretation of catalog merge history. The original live catalog-diff exporter should be rejected as the primary real-time mechanism.

However, the proposed design is not complete as written. The production recommendation is an enhanced write-time hybrid:

  1. Emit domain events at existing authoritative workflow checkpoints.
  2. Use one shared composite action only to validate and deliver event batches to Splunk HEC.
  3. Add centralized GitHub workflow telemetry for failures and cancellations that never reach those checkpoints.
  4. Use a periodic catalog snapshot reconciliation as a safety net.
  5. Use catalog history extraction only for a controlled one-time backfill.

This is an evolution of the hybrid recommendation: the catalog remains the authoritative final-state evidence, but live event creation happens where full context already exists.

Why write-time emission is better here

1. The workflow already derives the business payload

The image request workflow’s catalog-verification loop already resolves each requested image, normalized tag, catalog status, Artifactory path, and security-report link, then classifies the item as published, scan-gated, EOL, or not cataloged. That is exactly the information needed for an artifact outcome event.

The Windows request workflow has a similar post-run catalog lookup and checks both workflow conclusion and catalog state before it closes the issue. Helm downloads per-chart status artifacts and derives an individual result and reason. These are stronger semantic checkpoints than reconstructing intent from a later catalog commit.

2. Correlation exists before catalog persistence

IssueOps knows the issue number, request item, vendor, requested reference, dispatch run ID, and requester context. Those values do not reliably exist in catalog Git history. Capturing them at request time avoids an Actions API history lookup and avoids maintaining a run-ID-to-issue database.

3. Catalog history contains transport and tooling behavior

Catalog Git history records how automation merges and maintains files, not only business transitions. Merge commits and periodic metric-report commits are legitimate repository activity but introduce noise for a live event interpreter.

4. It matches the acceptance criteria

Request initiation, early validation failure, scan initiation, scan failure, and time-to-approval cannot be derived from a final catalog change. Write-time producers can emit those events at their authoritative boundaries.

Corrections required before adopting the new proposal

Correction 1 — a composite action cannot be invoked inside a shell loop. The existing verification is one large run: step. It should append normalized events to an NDJSON batch file and expose its path; the next workflow step invokes emit-telemetry once to send the batch.
catalog verification shell loop
  └── append one JSON event per artifact to telemetry-events.ndjson

following workflow step
  └── uses: ./.github/actions/emit-telemetry
      with:
        event-file: telemetry-events.ndjson
Correction 2 — request workflows do not observe every catalog mutation. Vendor lifecycles also run on schedules and can discover new releases without an issue. npm, PyPI, Helm, Windows, recurring scans, blackouts, and package merge paths mutate catalog state independently. The request-workflow checkpoints cover request-driven outcomes, not the complete publication universe.

For full “new releases detected” and catalog lifecycle reporting, either instrument the category-specific catalog-write checkpoints or accept that the reconciliation snapshot will report these later without request context. The latter is acceptable for an initial phase but not for real-time completeness.

Correction 3 — direct fail-soft delivery is not durable. Always exiting zero protects publication, but || true alone silently loses events. The action must return a delivery status, add a warning/job summary, and retain the failed batch as an artifact or otherwise make it replayable. Reconciliation protects final catalog state but cannot reconstruct every request or scan-start event.
Correction 4 — “full snapshot diff” needs durable state. A job cannot emit only changed hashes unless it has a reliable previous-hash store. The simplest safety net is to send a complete periodic snapshot to a separate sourcetype with a snapshot_id. If changed-only reconciliation is required, define a durable checkpoint store explicitly.
Correction 5 — one artifact ID is insufficient for generic or unresolved requests. At request initiation, a generic tag may not yet resolve to the final catalog version or digest. Use a durable request_item_id for the requested item and a separate resolved artifact_id when the concrete version is known.
Correction 6 — operational telemetry is still required. The proposed schema omits workflow-start/completion/cancellation events and detailed scan lifecycle events needed by the Operational Metrics dashboard. A central collector remains part of the final hybrid architecture.

Live mechanism

Use write-time emission for events where a workflow already knows the authoritative transition. Do not run a live catalog Git-history walker.

Safety net

Send a scheduled complete catalog snapshot, or a changed-only snapshot backed by a clearly defined durable hash store. Compare the snapshot with latest live artifact state in Splunk and alert on missing or inconsistent events.

Historical bootstrap

Use extract_from_catalog_commits.py once for backfill. Tag all such events source_type=backfill and document that request correlation is unavailable. Leave metrics-catalog.yml unchanged for its existing local reports.

Recommended identity and event schema

Retain the draft’s intersection fields and extra bag, but use two correlation identities:

  • request_item_id: created per artifact in an issue, such as a hash of repository, issue number, item index, and normalized requested reference. It exists before a concrete release is known.
  • artifact_id: identity of the resolved catalog artifact/version; include digest when it is stable and available, but do not require it for artifact kinds that lack one.

Additional files likely required for complete real-time coverage

The draft’s seven workflow targets do not cover all catalog writers. Scheduled vendor image lifecycles, npm/PyPI lifecycle catalog jobs, Helm lifecycle catalog commits, Windows lifecycle catalog commits, and blackout processing can change final artifact state without passing through the listed request outcome loops.

Expect updates to the production members of these categories:

  • Ten *-workflow-image-lifecycle.yml vendor workflows, unless their duplicated catalog-write logic is first centralized.
  • npm-library-workflow.yml and pypi-library-workflow.yml.
  • helm-charts-workflow.yml.
  • windows-pkg-microsoft-workflow-lifecycle.yml and windows-pkg-oracle-workflow-lifecycle.yml.
  • library-blackout-request-ops.yml.
  • Shared scan workflows or the remaining embedded scanner checkpoints needed for scan-start and scan-failure events.
Recommended scope control: do not edit all vendor lifecycles in Phase 1. Prove the event contract through image IssueOps, then centralize repeated event-building logic before expanding.

Implementation difficulty and effort

The composite action itself is not the difficult part. The hard work is defining stable semantics across artifact types, finding every authoritative checkpoint, maintaining per-artifact correlation through multi-item and scheduled runs, and proving that fail-soft telemetry is recoverable.

Verification requirements

  • Use a stand-in HEC receiver before production Splunk and assert exact request headers, batches, retries, timeouts and redaction.
  • Run a real test-vendor image request and confirm existing issue comments, closing behavior, publication and catalog output remain unchanged.
  • For a multi-image issue, verify one request_initiated and one terminal outcome per item, with distinct request_item_id values.
  • Verify that resolved generic tags link the initial request item to the concrete published artifact_id.
  • Test active, suppressed, inactive, EOL, not-cataloged, scanner failure, catalog failure and workflow cancellation outcomes.
  • Make HEC unreachable and confirm publication remains successful while the failed telemetry batch is visible and replayable.
  • Re-run the same workflow attempt and confirm deterministic event IDs prevent duplicate dashboard counts.
  • Run scheduled reconciliation and verify it identifies an intentionally omitted live event or out-of-band catalog edit.
  • Backfill a bounded time interval and confirm the backfill cutoff cannot overlap live events without deduplication.
  • Reconcile Splunk current whitelist totals against the catalog/ICEDevX source before accepting Dashboard 1.

Final decision

Choose the write-time checkpoint approach over the live catalog commit-diff exporter. It is a better fit for this repository because the workflows already possess the issue, artifact, status, scan, and publication context that the catalog history cannot reliably reconstruct.

Do not adopt the draft unchanged. Add a central workflow collector, use a dual request-item/artifact identity, batch events before invoking the composite action, make failed deliveries observable and replayable, and define a durable reconciliation model. Expand instrumentation deliberately because the request workflows alone do not cover every scheduled catalog writer.

Use the composite action as shared transport; use existing workflow checkpoints as domain-event producers; use catalog snapshots as reconciliation; use catalog history only for backfill.
