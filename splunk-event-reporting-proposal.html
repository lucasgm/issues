GitHub Actions events and Splunk reporting

A proposed design for reporting operational workflow health and authoritative third-party artifact outcomes without coupling Splunk availability to the scan-and-publish pipeline.

Recommended: catalog outcomes + centralized Actions collector

Executive decision

Use the catalog as the primary source for business and compliance reports, and add one centralized GitHub Actions collector for operational reports.

Do not add a Splunk composite action throughout every lifecycle workflow. A composite action may be useful as the shared HTTP Event Collector (HEC) client used by the two centralized exporters, but it should not define event semantics or be manually embedded in every scan, publish, and catalog job.

What the existing code shows

The platform has three different records of truth. They answer different reporting questions and should not be collapsed into a single workflow conclusion.

GitHub Actions

Did the workflow run, fail, cancel, retry, or exceed its expected duration?

Aqua and lifecycle jobs

What was scanned, what vulnerabilities were found, and did the immediate policy gate pass?

Third-party catalog

Was the artifact actually published, scan-gated, suppressed, made inactive, or omitted?

Key behavior: the image request workflow deliberately checks the catalog after the lifecycle run. It does not trust a green workflow conclusion because an EOL block, partial batch, or scan-gated artifact may still produce successful jobs.

The production flow spans vendor-specific image lifecycles, libraries, Helm charts, Windows packages, recurring scans, Artifactory promotion, signing, and catalog consolidation. The workflows do not share one uniform job graph, so per-workflow telemetry steps would create substantial maintenance and consistency risk.

Gaps in the existing catalog metrics pipeline

The current Catalog Metrics workflow and Python extractor provide a useful foundation, but should be corrected before they become a production Splunk feed.

1

The push trigger is attached to the automation repository. Catalog changes happen in a separate repository, so ingestion is effectively scheduled or manual rather than event-driven by catalog updates.

2

Every run reconstructs the full catalog history. This grows continuously and will resend events unless Splunk delivery has durable checkpoints and deterministic IDs.

3

Library results are omitted. The extractor scans containers, charts, and packages, but not vendor-catalog/library for npm and PyPI.

4

Removals and governance changes are missing. Blackouts, restores, suppression changes, suppression expiry, and deleted releases are not emitted as events.

5

Package rescan detection is incomplete. Packages compare policy-gate changes but do not consistently emit a new scan that retains the same gate result.

6

Run correlation is best-effort. The extractor parses run <digits> from free-form commit subjects instead of consuming structured provenance.

7

Event time is ambiguous. Catalog commit time and scan time must be preserved separately as observation time and occurrence time.

Proposed architecture

GitHub Actions / GitHub webhookWorkflow conclusion, attempt, duration, actor, failed job and run URL
→
Central operational exporterFilters production workflows, normalizes metadata, batches and retries HEC delivery
→
Splunk operational sourcetypeReliability, failure rate, cancellation, duration, queue and retry reporting
Catalog repository main branchAuthoritative JSON for containers, libraries, charts and packages
→
Incremental catalog exporterDiffs the pushed commit range and emits idempotent per-artifact outcomes
→
Splunk artifact sourcetypePublished, gated, suppressed, blacked out, removed, restored and rescanned

Catalog outcome exporter

  • Run from the catalog repository on changes to authoritative catalog paths.
  • Diff only the delivered commit range; use a scheduled reconciliation as recovery.
  • Normalize images, Helm charts, npm/PyPI libraries, and packages.
  • Require catalog status and Artifactory destination before reporting an artifact as published.
  • Send HEC batches with deterministic event IDs and retry transient errors.

Central Actions collector

  • Use one workflow_run: completed workflow scoped to production workflows, or an organization/repository webhook receiver.
  • Capture failures and cancellations that never produce catalog commits.
  • Query the Actions jobs API only when job-level failure and duration data are required.
  • Keep Splunk delivery failure non-blocking for artifact scanning and publication.

Shared event and correlation contract

Both streams should share stable keys so Splunk can correlate a failed workflow with catalog outcomes from the same request. Structured provenance should replace parsing run IDs from commit subjects.

Security and reliability requirements

  • Store the Splunk HEC token as an environment- or organization-scoped secret and mask it in all logs.
  • Allow only the internal Splunk endpoint and validate TLS; do not disable certificate verification.
  • Do not send credentials, raw issue bodies, full scan reports, or unrestricted workflow logs.
  • Apply payload size limits and batch events to reduce load on runners and HEC.
  • Use exponential backoff for retryable failures and deterministic IDs for safe replay.
  • Do not fail the scan, signing, promotion, or catalog workflow solely because Splunk is unavailable.
  • Alert separately when the exporter checkpoint falls behind the catalog or GitHub event stream.

Recommended rollout

Phase 1

Agree on event semantics, required reports, Splunk index and sourcetypes, retention, and the correlation fields.

Phase 2

Extend the existing extractor for incremental commit ranges, libraries, removals, blackout, suppression changes, and deterministic IDs.

Phase 3

Deploy the catalog exporter in the catalog repository and validate against current catalog reports before enabling HEC delivery.

Phase 4

Add the centralized Actions completion collector and correlate its run IDs with catalog event provenance.

Phase 5

Perform one controlled historical backfill, then enable scheduled reconciliation and exporter-lag alerting.

Success criterion: Splunk should answer both “Did the automation run successfully?” and “What happened to each requested artifact?” without interpreting a green workflow as proof of publication.
